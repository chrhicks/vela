# Vela

Chris Hicks's observing program. Read `SOUL.md` for how to work on it and `/home/chicks/dev/personal/home/AGENTS.md` for the house rules. This repo is public: no personal data, no real site coordinates, no real-night data. Fixtures use the made-up Phoenix site (latitude 33.45, longitude -112.07, elevation 331).

## What is here

Vela is being rebuilt on the rig stream (plan: `bots/observer/specs/vela-next/plan-v2.md` in the home repo). The old Vela was removed on 2026-11-07; what remains:

- `state/`: what the stream means, shared by the service and the web app (architecture: `bots/observer/specs/thuban-ui/architecture.md` in the home repo). `stream.ts` names the stream and its subjects from the `environment` setting (`dev` gives `RIG_DEV` and `rig-dev.*`); `entry.ts` reads a stream message into an entry (stream position, kind, time, body; command requests become `command` entries); `entries.ts` decodes the kinds the reducers use into typed entries with Effect Schema, once; `readings.ts` keeps each device property as the wire sends it, and `devices.ts` decodes each named device with its schema once, with INDI's property and element names, so the rest reads typed values; `wanted.ts` decides what the browser receives: the kinds `entries.ts` decodes and the properties `devices.ts` names, nothing listed by hand; `rig.ts` and one file per slice are the reducers, each with tests on made-up entries. `vela.started` is Vela's own entry, published once when the service starts, before the feed serves anything (`startAnnounced` in `src/bin/vela.ts`), carrying the start token; every reducer that holds work under way inside the previous process drops it when it meets the entry (a Start's steps are stopped, a capturing run and align or focus end interrupted, waiting presses are cleared, a flat test being tried is stopped, a review still waiting fails as restarted), and facts about the rig (readings, frames, stack, trends, last sweep, last calibration set) stay.
- `src/feed/`: the web app's event stream, in Effect. `Feed` holds the state folded from the wanted entries and passes on each new one; `GET /feed` (its own address, settings `feed.host` and `feed.port`) sends the state first with a token the service stamps at start (a page that sees a new token reloads), then each wanted entry and a heartbeat with the service's clock. A reconnect starts over with fresh state. `GET /targets?q=` (`targets.ts`, shapes in `state/targets.ts`) answers with the catalog targets a text finds and, when the mount has reported the site, where each is in the sky (`src/sky/placement.ts`: altitude, how long it stays above `pointing.upLineDegrees`, or when it rises to it, distance from the Moon). `GET /targets/best-placed?show=&order=` lists what to show with nothing typed (`src/catalog/placed.ts`): targets with a common name, at least `pointing.bestPlacedMinArcminutes` across and above the line now, all of them or only those hinted for dual band (`show`), the most cited or the largest first (`order`), cut to `pointing.bestPlacedRows` after that. Each listed or found target carries its size. `GET /sky` answers with tonight's hours of full darkness and the Moon: how much is lit, whether it is up, and when that changes (`src/sky/tonight.ts`). `GET /catalog` says how many targets the catalog holds, so the page can say when there is none. `GET /target?id=` answers with one target's facts: its other names, size, constellation, place and the dual-band hint (`src/catalog/dual-band.ts`). The same server serves the built web app (`feed.webRoot`, single-page fallback), so the page and its event stream come from one address; `deploy/install.sh` builds it.
- `src/catalog/`: the target catalog. No catalog data is in the repo: `src/bin/catalog-setup.ts` downloads the sources (`sources.ts`, one folder per source) and writes a SQLite file (`database.ts`, setting `catalog.database`) with each source's tables as they came and the views `targets` and `target_names`. Two sources: the Stellarium DSO Catalog, and OpenNGC for the NGC and IC objects it lacks (`openngc/derive.ts` decides which are the same object). `catalog.ts` reads the views at start and is the name search and the lookup by id. See its `README.md` and `ACKNOWLEDGEMENTS.md`.
- `src/sky/survey.ts`: the sky survey behind the picker's frame box. `src/bin/sky-setup.ts` downloads one HiPS order of a colour survey (settings `sky.address`, `sky.order`, `sky.tilesDir`) once, and carries on from the tiles already kept when run again. The service serves the tiles at `/sky-tiles/` and the survey's details at `GET /sky-survey`; no picture is fetched from outside when a target is chosen. The page cuts the field itself: `state/sky-cut.ts` is the HEALPix and tangent-plane arithmetic, with tests against values worked out independently. A second, finer survey (setting `skyDetail`, order 7, downloaded by `sky-setup.ts <config> detail`) is served at `/sky-detail-tiles/` and `GET /sky-detail-survey` for the picker's full-size view, which draws the tiles with WebGL2: `state/sky-mesh.ts` places each tile as a mesh on the tangent plane around the target and lists the tiles a view needs, and `web/src/routes/run/picker/sky-drawing.ts` keeps one texture per tile in view on the GPU, the coarse survey underneath and the fine one over it when the screen's scale is nearer to it. See `ACKNOWLEDGEMENTS.md`.
- `src/sky/coordinates.ts`: J2000 to epoch-of-date conversion (`toMount`, `fromMount`, `angularDistance`) on `astronomy-engine`. `src/sky/horizontal.ts` turns a wanted altitude and azimuth (azimuth east of north, geometric, no refraction) at a time and site into right ascension and declination of date.
- `src/bin/vela.ts`: the night page and capture controls, a Node service on thuban. `src/stream/` follows the stream (including command requests) as an Effect Stream: `Broker` is the connection as a scoped Layer, `followRig` replays from the rig's latest connection and marks when it has caught up, and its failures are typed (`BrokerUnreachable`, `StreamUnreadable`, `BrokerLost`, `FollowEnded`), `src/rig/` holds the picture (`picture.ts`) and what the page shows (`night.ts`), `src/page/` serves it. Deploy files in `deploy/`.
- `src/commands/`: the command sender (publish `rig-dev.command.<device>`, wait for the `client.command` answer). `src/capture/`: the capture run, the settings comparison, the run file and the `vela.run` entries. See the README.
- `src/prepare/`: the focuser and dew controls (`prepare.ts` checks a request against the limits on the stream and sends the commands) and the view the page draws them from (`view.ts`). PHD2's state and the time of its last guide step are on the page.
- `src/controls/start.ts`: Start on the picker. `startTarget` refuses at the press (unknown target, rig silent, mount or camera not reported, a run or a start already going), then runs the start routine in the background: set the cooler, home, stop guiding, slew and centre, autofocus, guide on a new star, then the light run, named by the target's catalog name. A press may carry a `centre` to slew to in place of the catalog centre (the picker's "as last time"); the run stays on the target. A press carries the `cooler` to start with, on at a setpoint or off: the routine sets it first, so the sensor cools through homing, centring and autofocus, and the light run asks for the same (on waits for the camera to report the setpoint reached, however long that takes; off turns it off). A setpoint outside the camera's reported range is refused at the press. Each step is one `vela.target.step` entry as it starts and as it ends (`state/starting.ts` folds them for the run page); a step that fails is reported with its refusal and the routine goes on; Stop, Home and the other presses that end a run stop it. Waits: `start.homeSeconds`, `start.guidingSeconds`. `refocus` and `reguide` (Refocus and Re-guide on the capturing page) pause the light run, wait until it has stepped off the camera, autofocus with the filter last answered or pick a guide star again and wait for guiding to settle, then carry the same run on, whatever the fix's outcome. A paused run lends the camera to one run (`src/capture/run.ts`), keeps its run file, sets the camera up again for its own frames when it carries on, and stops with that run on Stop.
- `src/remembered/`: what Vela remembers across restarts, folded from the stream's `vela.run` and `vela.centre` entries and the rig's measure answers (`src/stream/history.ts` reads them at start): the last light run's exposure and count, the camera angle of the latest solve, the centres centring runs reached, and the setpoint each light run on a target started with (a run started with the cooler off is not remembered, so it never becomes the default). The cooler is folded from the setpoint and cooler switch Vela wrote to the camera (`wire.<camera>.out`, read at start with the runs) and, when the cooler is on with no setpoint recorded, the rounded sensor temperature; a camera write later than a run is not applied to that run when entries replay. `GET /remembered` serves the first two; a target's facts carry its `lastCentre`, the latest centre reached within `pointing.sameFramingDegrees` of it, and its `lastCooler`, the target's own or else the latest of any target. The picker's Cooler row offers that setpoint, chosen, and Off; with nothing remembered it offers `controls.coolerCelsius`. The stream keeps 7 days, so the same facts are kept in the file `rememberedFile` (`kept.ts`): read at start with the stream folded on top, and written whenever they change.
- `src/pointing/`: catalog lookup to goto: `target.ts` converts a catalog row to epoch of date (precession and nutation, no site), `pointing.ts` sends goto, Unpark, Home, tracking and Stop and follows a goto from the stream, `goto.ts` is the move itself, shared with polar alignment: it takes right ascension and declination of date, sets `ON_COORD_SET` to TRACK, writes `EQUATORIAL_EOD_COORD` and waits for the property to go Busy then Ok, Idle or Alert. There is no Park (parking turns the rig sideways). `src/catalog/catalog.ts` is the lookup, `src/sky/meridian.ts` the time to the meridian limit.
- `src/frames/`: the frames: copy from the rig computer with a check, the sidecar, the stream entry, the FITS reader, the preview and crops at full size (`crop.ts`: the frame read once and kept while it is the one being looked at, each crop given every colour from its neighbours and the preview's brightness curves; served at `/frame-crop` and `/frame-shape` by `src/feed/crops.ts`). See the README.
- `src/review/` and `state/review*.ts`: the frame review, report only. `review.ts` follows the stream, and for each light frame of a target run, once its `vela.frame` entry says it is kept, makes the frame's preview (`image.ts`: a downscaled PNG with no metadata chunks, long side at most `review.imageLongSide`) and asks every model in `review.models` at once, each through `Reviewer` (`reviewer.ts`, `@anthropic-ai/sdk`, no credentials in code: it takes ANTHROPIC_API_KEY, ANTHROPIC_AUTH_TOKEN or the sign-in from `ant auth login`). A request is one image and one question (`request.ts`: the frame's exposure and `review.hazards`), nothing else: no stats, target, pointing, site, time or FITS header, and its test checks that. The structured answer (`answer.ts`: obstructed, confidence, hazard from the hazards setting or none or other, one sentence) is decoded with Effect Schema; every failure is a typed answer that is recorded and logged once, never a crash, and never touches capture or the other model. Each ask and answer is a stream entry (`vela.review.asked`, `vela.review.answer`) and a line in `review.answersFile`, since the stream keeps 7 days. Replayed history is not asked about again. It never acts on the rig.
- `compose.yaml` and `deploy/nats.conf`: the NATS broker that carries the rig stream. It has no logins and nothing to provision; the rig program creates the `RIG_DEV` stream.
- `web/`: the web app that will replace the night page: React, built by Vite, its own package in the pnpm workspace. The routes (`/` the run, `/launch`, `/controls`, `/review`), the shared components and the style tokens. `web/src/rig/` follows the service's event stream (`feed.ts`, an Effect Stream decoding each message with `state/feed.ts`) into a small store (`store.ts`: `useRig`, `useLink`; a new start token reloads the page). Which screens are on real data and which still read stubs: `web/README.md`.
- `verify.sh`: typecheck and tests, then the web app's typecheck and build.

The broker's data (`~/.local/share/vela/nats`), Vela's saved images and its archives are data on disk. Nothing in this repo deletes them.

## Rules

- The service under `src/` is run from source by Node 26 with no build step; style follows Cria's `ts/`. Only `web/` is built.
- Non-React code uses Effect: Schema decodes at every boundary, ids are branded, failures are typed errors. React gets Promises from hooks. Old code runs an Effect only through `src/edge.ts` (`runHandledSync`, `runHandledPromise`), which accept only an Effect whose errors are all handled, so an unhandled error is a compile error. The shared coding standard (TypeScript) owns the rule; files move to it as they are touched, and `src/stream/json.ts` holds the old hand-written readers until then.
- `state/` and `web/` decode once and then trust the types. The schemas are the lists: entry kinds and bodies in `entries.ts`, wire fields in `entry.ts`, device properties in `devices.ts`. No `typeof`, `in`, hand-written `x is T` guards, name or prefix checks, or string compares on a value that is not decoded yet, and no `as const`: a closed set of values is a `Schema.Literals` (its `.literals` is the list), anything else gets a declared type. A new kind, field or value gets its schema first; anything the schema rejects is a typed error, never quietly dropped. The service's older readers in `src/` (`src/stream/json.ts`, `recordOf`) are not an example to copy.
- No comments in code: a limit or default is a described setting, a surprise is a better name or type.
- Run `./verify.sh` before a PR.
