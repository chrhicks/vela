# Vela

Chris Hicks's observing program. Read `SOUL.md` for how to work on it and `/home/chicks/dev/personal/home/AGENTS.md` for the house rules. This repo is public: no personal data, no real site coordinates, no real-night data. Fixtures use the made-up Phoenix site (latitude 33.45, longitude -112.07, elevation 331).

## What is here

Vela is being rebuilt on the rig stream (plan: `bots/observer/specs/vela-next/plan-v2.md` in the home repo). The old Vela was removed on 2026-11-07; what remains:

- `state/`: what the stream means, shared by the service and the web app (architecture: `bots/observer/specs/thuban-ui/architecture.md` in the home repo). `stream.ts` names the stream and its subjects from the `environment` setting (`dev` gives `RIG_DEV` and `rig-dev.*`); `entry.ts` reads a stream message into an entry (stream position, kind, time, body; command requests become `command` entries); `entries.ts` decodes the kinds the reducers use into typed entries with Effect Schema, once; `readings.ts` keeps each device property as the wire sends it, and `devices.ts` decodes each named device with its schema once, with INDI's property and element names, so the rest reads typed values; `wanted.ts` decides what the browser receives: the kinds `entries.ts` decodes and the properties `devices.ts` names, nothing listed by hand; `rig.ts` and one file per slice are the reducers, each with tests on made-up entries. `vela.started` is Vela's own entry, published once when the service starts, before the feed serves anything (`startAnnounced` in `src/bin/vela.ts`), carrying the start token; every reducer that holds work under way inside the previous process drops it when it meets the entry (a Start's steps are stopped, a sweep rehearsal is ended, a capturing run and align or focus end interrupted, waiting presses are cleared, a flat test being tried is stopped, a review still waiting fails as restarted), and facts about the rig (readings, frames, stack, trends, last sweep, last calibration set) stay.
- `src/feed/`: the web app's event stream, in Effect. `Feed` holds the state folded from the wanted entries and passes on each new one; `GET /feed` (its own address, settings `feed.host` and `feed.port`) sends the state first with a token the service stamps at start (a page that sees a new token reloads), then each wanted entry and a heartbeat with the service's clock. A reconnect starts over with fresh state. `GET /targets?q=` (`targets.ts`, shapes in `state/targets.ts`) answers with the catalog targets a text finds and, when the mount has reported the site, where each is in the sky (`src/sky/placement.ts`: altitude, how long it stays above the horizon at its azimuth, or when it rises to it, distance from the Moon). Up means above `altitudeAt(horizon, azimuth)` from the horizon file read once at start, and above `pointing.upLineDegrees` where the file is missing or has no edge at that azimuth (each placement says which: `lineSource`, and a rise or until time says which line it crossed, `lineSource` and `lineDegrees` inside the `until` or `rises` line). The rise and until times come from stepping the target through the next `pointing.upLookAheadHours` every `pointing.upStepSeconds` and finding where its altitude crosses the horizon at its azimuth then, to the second between two steps. `GET /targets/best-placed?show=&order=` lists what to show with nothing typed (`src/catalog/placed.ts`): targets with a common name, at least `pointing.bestPlacedMinArcminutes` across and above the line now, all of them or only those hinted for dual band (`show`), the most cited or the largest first (`order`), cut to `pointing.bestPlacedRows` after that. Each listed or found target carries its size. `GET /sky` answers with tonight's hours of full darkness and the Moon: how much is lit, whether it is up, and when that changes (`src/sky/tonight.ts`). `GET /catalog` says how many targets the catalog holds, so the page can say when there is none. `GET /target?id=` answers with one target's facts: its other names, size, constellation, place and the dual-band hint (`src/catalog/dual-band.ts`). `GET /horizon-night?target=ID&at=ISO` (`src/feed/horizon-night.ts`, shapes in `state/horizon-night.ts`, composed in `src/catalog/horizon-night.ts`, `at` defaults to now) answers with one target's night, computed per request: the night `at` falls in (`nightTimes`, the coming night after dawn or before dusk), named for its evening in the `frames.nightZone` zone, with dusk, dark, dark ends and dawn; the 360 horizon bins with their sources, the nights of the sweeps they came from (`sweepNights`) and whether a horizon file was loaded; the target's path from dusk to dawn every `horizonNight.stepSeconds` as parallel arrays rounded to `horizonNight.decimals` (`altitudes`, `azimuths`, `lines`, the line being the horizon at that azimuth or `pointing.upLineDegrees` where unmapped); every spell that is both dark and above the line, with what started and ended it (`dark`, `trees` with an 8-point compass direction, `up-line`, `horizon`); the Moon on the same steps (`moon`: `altitudes` and `azimuths` with refraction, so it is up where the altitude is above 0, the rule of `skyTonight`; `litFraction` at the middle of the night; `upSpans`, the spans inside the night where it is up, whose ends are its rise and set; `src/sky/moon-night.ts`); the camera frame (`frame`: the remembered camera angle or null, the direction of celestial north measured from straight up toward increasing azimuth on each step, rounded to `horizonNight.frameAngleDecimals`, and `firstCleanAt`, the first time in full darkness when the whole footprint of the camera field is above the line; `src/sky/frame-night.ts` projects the footprint from the J2000 tangent plane through the sky at that time, and checks its lowest edge against the line at every whole degree of azimuth it spans, just either side of it, and at each of its `horizonNight.frameEdgeSamples` points per edge, finding the time to the second); and the facts (the spell holding `at`, else the next one, the highest altitude and its time and the transit from the samples, and the flip, predicted from the mount's `MERIDIAN_LIMIT` when the rig has reported it and otherwise from the meridian, labelled which). It refuses with `malformed` (400), `unknown-target` (404), `no-site` (503, the mount has not reported `GEOGRAPHIC_COORD`) or `no-night` (422, the Sun does not set or rise). The camera field is `frameDegrees` in `state/frame-field.ts`, and `state/horizon-frame.ts` turns it by the camera angle and places it round a point of the sky from that direction of north, which is how the page draws the footprint at any time. The position and clearance arithmetic is `src/sky/path.ts`, shared by `placementOf` and the night (`src/sky/target-night.ts`). The same server serves the built web app (`feed.webRoot`, single-page fallback), so the page and its event stream come from one address; `deploy/install.sh` builds it.
- `src/forecast/`: the cloud forecast for the site the mount reports, served at `GET /forecast?at=ISO` (`src/feed/forecast.ts`, shapes in `state/forecast.ts`, `at` defaults to now and picks the night as `/horizon-night` does). The answer is one entry per whole hour from dusk to dawn: `coverPercent` (0 is a value, `null` is unknown) and its `source` (`nws` or `open-meteo`), the `cloudyPercent` the page greys from (`horizonNight.cloudyPercent`), and for each source the age in seconds of its last answer and whether its latest refresh failed. It refuses with `malformed` (400), `no-site` (503) or `no-night` (422). `forecasts.ts` looks up the National Weather Service grid point once for the site (kept in memory, tried again after `forecast.retryMinutes` when it fails), reads the grid's `skyCover` with each `validTime` interval expanded to its hours (`cover.ts`), and asks Open-Meteo for `cloud_cover` only when an hour of the night has no National Weather Service value. Each source is asked again `forecast.refreshMinutes` after it answered; a request is answered from what is kept while a refresh runs behind it, except the first for a site, which waits for it. A failed refresh keeps the last answer for the same site and reports its age; a different site starts empty. Requests carry `User-Agent: forecast.userAgent` and the position rounded to `forecast.positionDecimals` places, built at request time and never logged or written; the only things logged are a source going unavailable and coming back. `source.ts` is the one place that fetches.
- `src/catalog/`: the target catalog. No catalog data is in the repo: `src/bin/catalog-setup.ts` downloads the sources (`sources.ts`, one folder per source) and writes a SQLite file (`database.ts`, setting `catalog.database`) with each source's tables as they came and the views `targets` and `target_names`. Two sources: the Stellarium DSO Catalog, and OpenNGC for the NGC and IC objects it lacks (`openngc/derive.ts` decides which are the same object). `catalog.ts` reads the views at start and is the name search and the lookup by id. See its `README.md` and `ACKNOWLEDGEMENTS.md`.
- `src/sky/survey.ts`: the sky survey behind the picker's frame box. `src/bin/sky-setup.ts` downloads one HiPS order of a colour survey (settings `sky.address`, `sky.order`, `sky.tilesDir`) once, and carries on from the tiles already kept when run again. The service serves the tiles at `/sky-tiles/` and the survey's details at `GET /sky-survey`; no picture is fetched from outside when a target is chosen. The page cuts the field itself: `state/sky-cut.ts` is the HEALPix and tangent-plane arithmetic, with tests against values worked out independently. A second, finer survey (setting `skyDetail`, order 7, downloaded by `sky-setup.ts <config> detail`) is served at `/sky-detail-tiles/` and `GET /sky-detail-survey` for the picker's full-size view, which draws the tiles with WebGL2: `state/sky-mesh.ts` places each tile as a mesh on the tangent plane around the target and lists the tiles a view needs, and `web/src/routes/run/picker/sky-drawing.ts` keeps one texture per tile in view on the GPU, the coarse survey underneath and the fine one over it when the screen's scale is nearer to it. See `ACKNOWLEDGEMENTS.md`.
- `src/sky/coordinates.ts`: J2000 to epoch-of-date conversion (`toMount`, `fromMount`, `angularDistance`) on `astronomy-engine`. `src/sky/horizontal.ts` turns a wanted altitude and azimuth (azimuth east of north, geometric, no refraction) at a time and site into right ascension and declination of date.
- `src/bin/vela.ts`: the night page and capture controls, a Node service on thuban. `src/stream/` follows the stream (including command requests) as an Effect Stream: `Broker` is the connection as a scoped Layer, `followRig` replays from the rig's latest connection and marks when it has caught up, and its failures are typed (`BrokerUnreachable`, `StreamUnreadable`, `BrokerLost`, `FollowEnded`), `src/rig/` holds the picture (`picture.ts`) and what the page shows (`night.ts`), `src/page/` serves it. Deploy files in `deploy/`.
- `src/commands/`: the command sender (publish `rig-dev.command.<device>`, wait for the `client.command` answer). `src/capture/`: the capture run, the settings comparison, the run file and the `vela.run` entries. See the README.
- `src/prepare/`: the focuser and dew controls (`prepare.ts` checks a request against the limits on the stream and sends the commands) and the view the page draws them from (`view.ts`). PHD2's state and the time of its last guide step are on the page.
- `src/controls/start.ts`: Start on the picker. `startTarget` refuses at the press (unknown target, rig silent, mount or camera not reported, a run or a start already going), then runs the start routine in the background: set the cooler, home, stop guiding, slew and centre, autofocus, guide on a new star, then the light run, named by the target's catalog name. A press may carry a `centre` to slew to in place of the catalog centre (the picker's "as last time"); the run stays on the target. A press carries the `cooler` to start with, on at a setpoint or off: the routine sets it first, so the sensor cools through homing, centring and autofocus, and the light run asks for the same (on waits for the camera to report the setpoint reached, however long that takes; off turns it off). A setpoint outside the camera's reported range is refused at the press. Each step is one `vela.target.step` entry as it starts and as it ends (`state/starting.ts` folds them for the run page); a step that fails is reported with its refusal and the routine goes on; Stop, Home and the other presses that end a run stop it. Waits: `start.homeSeconds`, `start.guidingSeconds`. `refocus` and `reguide` (Refocus and Re-guide on the capturing page) pause the light run, wait until it has stepped off the camera, autofocus with the filter last answered or pick a guide star again and wait for guiding to settle, then carry the same run on, whatever the fix's outcome. A paused run lends the camera to one run (`src/capture/run.ts`), keeps its run file, sets the camera up again for its own frames when it carries on, and stops with that run on Stop.
- `src/controls/rehearse.ts`: Rehearse sweep on Controls (Mount panel), the indoor rehearsal of the horizon sweep, with no frames. `rehearseSweep` refuses at the press (rig silent, mount or its site or position not reported, a run, Start, alignment or another rehearsal going), then in the background chains legs from where the mount is to the first pose of `rehearsalRoute` and visits every pose in order with the shared goto (`src/pointing/goto.ts`), the right ascension of date worked out from each pose's hour angle at move time. Each move is one `vela.sweep.move` entry (column, altitude and azimuth, hour angle and declination asked, predicted pier side and whether a flip was expected, the outcome, and the mount's `EQUATORIAL_EOD_COORD` and `TELESCOPE_PIER_SIDE` once it has answered); a move the mount answers with an alert or the rig refuses is recorded and the rehearsal goes on. `vela.sweep.started` and `vela.sweep.ended` carry the total and how it ended: finished, `stopped` (Stop), `pressed` (Home, Slew and centre, Stop for the night or autofocus), or `restarted` (`vela.started`, folded by `state/rehearsal.ts`, which the Mount panel's feedback line reads). It leaves the mount where it is. Start refuses while a rehearsal is going.
- `src/controls/sweep.ts`: Sweep on Controls (Mount panel, with an exposure, default `controls.testFrameSeconds`), the real horizon sweep. `startSweep` refuses like the rehearsal (rig silent, mount or its site or position not reported, a rehearsal, sweep, run or Start going), stops PHD2 guiding if it is guiding, starts one light run named `horizon-sweep` through `src/sweep/frames.ts` and forks the routine, tracked by the same `RehearsalRunning` as the rehearsal (one routine at a time; Stop, Home, Slew and centre, Stop for the night and autofocus end it, `vela.started` ends it as `restarted`). For each column of `columns` (east half round to the north, then the west half) it follows the edge: each move is `legs` from the last pose, each leg a plain goto (the mount flips itself on the first goto past the meridian), `sweep.settleSeconds`, then one frame of the exposure, measured for solve and stars with `keep`, so the rig computer moves it into the spool and the keeper copies it with the other lights. A frame that solved is sky and one that did not is blocked; its star count and a baseline (`src/sweep/baseline.ts`: the median of the top `baselineTopFraction` of the run's solved frames within `baselineAltitudeDegrees` of its altitude, else the best solved count so far) are recorded beside the class and decide nothing. `src/sweep/column.ts` picks the next altitude (`stepDegrees` lower after sky, higher after blocked; a sky/blocked change between two consecutive frames or the floor or ceiling ends the column, the edge being the midpoint of the frames' pointing altitudes; `alertAfterFrames` in one column publishes an alert and goes on). The next column starts at the midpoint of the altitudes the two bracketing frames were commanded at, so the pointing error does not move the start, and the first column of the west half starts from the first column of the east half. `src/sweep/pointing.ts` the altitude and azimuth a frame is taken to have: the solve (J2000 centre taken to altitude and azimuth at the exposure middle), else the commanded position plus the offset of the latest solved frame on the same pier side. Entries: `vela.sweep.run.started`, `vela.sweep.frame`, `vela.sweep.column`, `vela.sweep.alert`, `vela.sweep.run.ended` (`state/sweep.ts` folds them for the feedback line), and each frame and column is also appended to `frames.jsonl` and `columns.jsonl` in `<sweep.recordDir>/<night>/`; a write that fails is an alert. `src/sweep/frames.ts` gates the one capture run so a frame is exposed only when the routine asks and answers with the measure answer for that frame; the stack leaves `horizon-sweep` frames out.
- `src/bin/sweep-cells.ts` (`node src/bin/sweep-cells.ts <config.json> <night> [--sweep ID-PREFIX] [--out FOLDER]`): labels the cells of a night's kept sweep frames on thuban, offline, never during a sweep. For each frame of `<sweep.recordDir>/<night>/frames.jsonl` (the sweeps whose id starts with the prefix) it runs ASTAP's `-extract` on the kept frame in `<frames.keepDir>/<night>/` (through a symlink in a temporary folder, so nothing is written beside the frame, and the name has no dot for ASTAP to cut at; the program and signal to noise are the `stars` setting), splits the frame into `sweep.cells.columns` by `sweep.cells.rows` cells (`src/sweep/cells.ts`), counts the stars and takes the median pixel level in each, and labels each cell sky, partly blocked or blocked by its star count against the clear-sky count of a cell (`blockedBelow`, `partlyBlockedBelow`). The clear-sky count is the median of the frame's own best cells (`clearTopFraction`) when it solved, and for a frame that did not, the higher of that and the baseline (`src/sweep/baseline.ts`, fed the solved frames' own clear-sky counts). Each cell centre is placed in altitude and azimuth at the exposure middle (`src/sweep/projection.ts`: the solve's centre, rotation and scale as a tangent plane, ASTAP's pixel positions counted from 1 and rows as stored; an unsolved frame uses its recorded pointing as the centre, the scale from the header and the rotation of the nearest solved frame on the same pier side) for the site in the frame's own `SITELAT` and `SITELONG` header (the camera driver writes the mount's site there; `SITEELEV` when present, else 0); a sweep none of whose frames has them is left out and named. `src/sweep/edges.ts` gives each `sweep.cells.edgeBinDegrees` bin of azimuth its edge: the cut in altitude with the fewest sky and blocked cells on the wrong side of it (partly blocked cells do not vote), at the middle of the gap between the cells either side; with clean labels that is halfway between the highest blocked cell and the lowest sky cell, and one noisy blocked cell high in the sky does not raise it. `misfits` is how many cells were on the wrong side; a bin of sky only is `open` and one of blocked only is `blocked`. The output, written whole each run into `--out` (default the night's record folder, beside `frames.jsonl`): `cells.jsonl` (a line per frame: its clear-sky count and where that came from, how it was placed, and each cell's count, level, label and place) and `edges.jsonl` (a line per bin of each sweep). A frame ASTAP or the file cannot give is left out and named. `src/sweep/cell-night.ts` is the I/O, `labelling.ts` the pure part, `cell-record.ts` the line schemas.
- `src/bin/sweep-horizon.ts` (`node src/bin/sweep-horizon.ts <config.json> <night> [--sweep ID-PREFIX] [--out FILE]`): builds the horizon file from one sweep's records in `<sweep.recordDir>/<night>/`, offline, never during a sweep. The prefix must match one sweep; the command says which match when it does not. Each 1 degree bin takes its cell edge from `edges.jsonl` (`how` `edge`); a bin with none takes the `edgeAltitudeDegrees` of the column in `columns.jsonl` whose span (`sweep.columnDegrees` about the column's azimuth) covers its centre, the nearer when two do, leaving out a column that was `blocked-to-ceiling`; a bin with neither is left as it was (null in a new file), which is unknown, not open sky. `edges.jsonl` may be missing, and the columns alone are used. Every bin it gives has source `sweep` and the time of the last frame of the column over it (from `frames.jsonl`; a cell edge takes the nearest column's time when none spans it), and its origin: the sweep's full id and the night, so the records behind the bin are `<sweep.recordDir>/<night>/` filtered to that sweep. The output is the version 2 file at `--out` (default the `horizonFile` setting): when the file is already there it is read first (an unreadable one is left alone and named), only the bins this sweep gives are replaced, the others keep their altitude, source, time and origin, and a copy of the old file is written beside it as `<file>.bak-<time>` before the new one replaces it. `src/sweep/horizon-build.ts` is the pure part, `horizon-night.ts` the I/O.
- `src/horizon/`: the horizon file, version 2 (`horizon.ts` the schema, `noHorizon` and the pure `altitudeAt(horizon, azimuthDegrees)`; `file.ts` reads it from the `horizonFile` setting). 360 one-degree bins of altitude in degrees, each with its source (`sweep`, `frames` or `old-profile`), the time it was observed and its origin (`origins`: the `sweep` id and the `night` whose records directory holds that sweep, so a bin's frames and edges can be found); a bin is null where unknown. `origins` is optional in the file: a file written before it existed reads as every origin null, and a bin of a later build that the sweep did not give keeps whatever origin it had. `altitudeAt` interpolates between the two bins around an azimuth, wrapping at 360, and is null when either is unknown. A missing file is no horizon (unknown everywhere); an unreadable or invalid file is `HorizonUnreadable`, which `loadHorizon` logs once and treats as no horizon. `src/catalog/placed.ts` reads it once at start (`loadHorizon` in `src/bin/vela.ts`, a missing file logged once as well); a new file is picked up at a restart. `GET /horizon-sweep` (`src/feed/horizon-sweep.ts`, shapes in `state/horizon-sweep.ts`) serves what the tree map draws, read once at start by `src/sweep/horizon-map.ts` from `<sweep.recordDir>/<night>/` for the sweeps and nights the horizon's `origins` name, each night's files read once and filtered to those sweeps: from `frames.jsonl` each frame's pointing (altitude, azimuth, source) and class, from `edges.jsonl` each bin's edge kind (`edge`, `open`, `blocked`; null where the origin is null or the sweep has no row for the bin), and the nights, nothing else. Without any origin, or with a file missing, a line of the named sweeps that does not decode, or none of the named sweep's rows, it answers `unavailable` with the reason (`no-origins`, `missing`, `unreadable`, `no-frames`, `no-edges`), the night and the file; the log line at start gives the read time and the answer's size. The horizon page's chip D draws the frames (+ clean, ■ blocked, fainter the less measured the pointing) and the tree line dotted where a bin or its neighbour has no cell edge (`state/horizon-sweep-view.ts`).
- `src/sweep/`: the horizon sweep's path, pure functions with no I/O (`path.ts`, settings in `settings.ts` under `sweep`); only the rehearsal below calls them. A pose is an hour angle and declination, which depend only on the site's latitude (right ascension of date is worked out at move time from the hour angle), with its altitude and azimuth and the pier side predicted from the meridian limit. `columns` lists the azimuth columns (south, east round to the north, then west round to the north), `legs` splits a move so neither axis turns more than `sweep.legDegrees`, and `rehearsalPath` is every move of the indoor rehearsal with the expected flips marked. `rehearsalRoute` chains legs from the pose the mount is at to the first rehearsal pose and then follows `rehearsalPath`.
- `src/remembered/`: what Vela remembers across restarts, folded from the stream's `vela.run` and `vela.centre` entries and the rig's measure answers (`src/stream/history.ts` reads them at start): the last light run's exposure and count, the camera angle of the latest solve, the centres centring runs reached, and the setpoint each light run on a target started with (a run started with the cooler off is not remembered, so it never becomes the default). The cooler is folded from the setpoint and cooler switch Vela wrote to the camera (`wire.<camera>.out`, read at start with the runs) and, when the cooler is on with no setpoint recorded, the rounded sensor temperature; a camera write later than a run is not applied to that run when entries replay. `GET /remembered` serves the first two and the shortlist (`shortlist`); a target's facts carry its `lastCentre`, the latest centre reached within `pointing.sameFramingDegrees` of it, and its `lastCooler`, the target's own or else the latest of any target. The picker's Cooler row offers that setpoint, chosen, and Off; with nothing remembered it offers `controls.coolerCelsius`. The shortlist is the targets the user picks with the `shortlist` command (add or remove one catalog id, published as the `vela.shortlist` entry on `rig-dev.vela.shortlist`, which startup replays with the runs). Until the first edit it is the most recent targets a light run on a target kept a frame for (`vela.run.exposed`; targets only the older `targetCoolers` know follow them), newest first, `shortlist.recentCount` of them, leaving out typed positions and ids the catalog does not hold; the first edit records the list shown as `from`, so the kept `shortlist` is `undefined` for never edited and `[]` for emptied, and replaying edits over a kept list is safe (adds and removes are set operations in order). `GET /horizon-paths?targets=a,b,c&at=ISO` answers with each known target's path only (`state/horizon-night.ts` `HorizonPaths`; unknown ids are listed under `unknown`), not the Moon, horizon and frame that `/horizon-night` repeats. The stream keeps 7 days, so the same facts are kept in the file `rememberedFile` (`kept.ts`): read at start with the stream folded on top, and written whenever they change.
- `src/pointing/`: catalog lookup to goto: `target.ts` converts a catalog row to epoch of date (precession and nutation, no site), `pointing.ts` sends goto, Unpark, Home, tracking and Stop and follows a goto from the stream, `goto.ts` is the move itself, shared with polar alignment: it takes right ascension and declination of date, sets `ON_COORD_SET` to TRACK, writes `EQUATORIAL_EOD_COORD` and waits for the property to go Busy then Ok, Idle or Alert. There is no Park (parking turns the rig sideways). `src/catalog/catalog.ts` is the lookup, `src/sky/meridian.ts` the time to the meridian limit.
- `src/frames/`: the frames: copy from the rig computer with a check, the sidecar, the stream entry, the FITS reader, the preview and crops at full size (`crop.ts`: the frame read once and kept while it is the one being looked at, each crop given every colour from its neighbours and the preview's brightness curves; served at `/frame-crop` and `/frame-shape` by `src/feed/crops.ts`). See the README.
- `src/review/` and `state/review*.ts`: the frame review, report only. `review.ts` follows the stream, and for each light frame of a target run, once its `vela.frame` entry says it is kept, makes the frame's preview (`image.ts`: a downscaled PNG with no metadata chunks, long side at most `review.imageLongSide`) and asks every model in `review.models` at once, each through `Reviewer` (`reviewer.ts`, `@anthropic-ai/sdk`, no credentials in code: it takes ANTHROPIC_API_KEY, ANTHROPIC_AUTH_TOKEN or the sign-in from `ant auth login`). A request is one image and one question (`request.ts`: the frame's exposure and `review.hazards`), plus one sentence when the mapped horizon is known where the frame points: how far the frame's centre sits above or below the mapped line at its azimuth, and how tall the frame is (`line.ts`, `place.ts`: the frame's solve from its stats file, else the mount's position in its header, taken at the middle of the exposure, set against `altitudeAt`). Nothing else goes: no stats, target, pointing, site, time, azimuth, altitude or FITS header, and its test checks that. Where the horizon has no value at the frame's azimuth the question is as it was. Each answer entry carries the frame's `line` (centre and lowest margin, height, source), and an obstructed answer with some of the frame below the line shows as "behind the trees" on the page; without a line it stays the open question. Old answer lines have no `line` and still decode. The structured answer (`answer.ts`: obstructed, confidence, hazard from the hazards setting or none or other, one sentence) is decoded with Effect Schema; every failure is a typed answer that is recorded and logged once, never a crash, and never touches capture or the other model. Each ask and answer is a stream entry (`vela.review.asked`, `vela.review.answer`) and a line in `review.answersFile`, since the stream keeps 7 days. Replayed history is not asked about again. It never acts on the rig.
- `compose.yaml` and `deploy/nats.conf`: the NATS broker that carries the rig stream. It has no logins and nothing to provision; the rig program creates the `RIG_DEV` stream.
- `web/`: the web app that will replace the night page: React, built by Vite, its own package in the pnpm workspace. The routes (`/` the run, `/launch`, `/controls`, `/review`, `/horizon?target=ID`), the shared components and the style tokens. `web/src/rig/` follows the service's event stream (`feed.ts`, an Effect Stream decoding each message with `state/feed.ts`) into a small store (`store.ts`: `useRig`, `useLink`; a new start token reloads the page). Which screens are on real data and which still read stubs: `web/README.md`.
- `verify.sh`: typecheck and tests, then the web app's typecheck and build.

## Rules

- The service under `src/` is run from source by Node 26 with no build step; style follows Cria's `ts/`. Only `web/` is built.
- Non-React code uses Effect: Schema decodes at every boundary, ids are branded, failures are typed errors. React gets Promises from hooks. Old code runs an Effect only through `src/edge.ts` (`runHandledSync`, `runHandledPromise`), which accept only an Effect whose errors are all handled, so an unhandled error is a compile error. The shared coding standard (TypeScript) owns the rule; files move to it as they are touched, and `src/stream/json.ts` holds the old hand-written readers until then.
- `state/` and `web/` decode once and then trust the types. The schemas are the lists: entry kinds and bodies in `entries.ts`, wire fields in `entry.ts`, device properties in `devices.ts`. No `typeof`, `in`, hand-written `x is T` guards, name or prefix checks, or string compares on a value that is not decoded yet, and no `as const`: a closed set of values is a `Schema.Literals` (its `.literals` is the list), anything else gets a declared type. A new kind, field or value gets its schema first; anything the schema rejects is a typed error, never quietly dropped. The service's older readers in `src/` (`src/stream/json.ts`, `recordOf`) are not an example to copy.
- No comments in code: a limit or default is a described setting, a surprise is a better name or type.
- Run `./verify.sh` before a PR.
